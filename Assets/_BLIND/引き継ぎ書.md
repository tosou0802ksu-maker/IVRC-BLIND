## 1. プロジェクト概要

**BLIND** — VRChat上の3人非対称協力ホラー探索ゲーム。IVRC2026 メタバース部門応募作品。

3人のプレイヤーは**それぞれ違う世界を見ている**。同じ部屋にいるのに、見えているものが一人ずつ全く違う。
声で伝え合わないと一歩も進めない、というのがこの作品の中心にある仕掛け。

| 役割 | 見えるもの | 担当する情報 |
|---|---|---|
| **エコロケ** | 音波パルスが当たった面の**輪郭だけ**が数秒光る。それ以外は暗闇 | 空間の**形**（壁・段差・通路・什器の配置） |
| **サーモ** | **熱源だけ**が色で見える。建物はほぼ真っ黒 | **危険と生き物**（炎・人・通電した機器・水） |
| **過去人** | 普通の照明つきの世界。ただし**「今」は見えず「かつてそこにあったもの」**が見える | **意味**（看板・文字・矢印・記憶） |

世界観はリミナルスペース／バックルームズ系（単調な蛍光灯、反復するオフィス、朽ちたプール）。
**ここのクオリティには妥協しない**というのが作者の明言した方針。技術的な都合で雰囲気を削る提案は歓迎されない。

## 3. 最重要アーキテクチャ：「3つの世界」

**これを理解していない改修は100%壊れる。**

| Layer | 名前 | 誰に見えるか |
|---|---|---|
| 0 | Default | **過去人だけ** |
| 22 | Thermal | **サーモだけ** |
| 23 | Echo | **エコロケだけ** |
| 24 | Memory | 過去人だけ（看板・矢印・クイズの文字） |

各役割のカメラは**自分のレイヤーだけを映し、背景は黒**。
つまり「壁は全員に見える」のではない。**同じ壁を3枚、レイヤー違いで重ねて置いている。**

```
Box_Root                     ← 位置と Collider はここに1つだけ
 ├ Vis_Default   (Layer 0)   ← 普通の見た目
 ├ Vis_Echo      (Layer 23)  ← EchoHighlight マテリアル
 └ Vis_Thermal   (Layer 22)  ← Thermal_*.mat
```

この重複メッシュを**手で置くのは不可能**（部屋19個・レンダラー数千個）なので、
Default層のジオメトリから **Thermal層とEcho層を自動生成するツール**を作ってある。それが §4。

### ⚠️ VRChat実機の落とし穴（既に踏んで解決済み）
シーンに置いた `Camera.cullingMask` を書き換えても**実機では何も起きない**。
`VRC.SDK3.Rendering.VRCCameraSettings.ScreenCamera.CullingMask` を書き換える必要がある。
`PlayerVisionController.cs` は修正済み。`OnVRCCameraSettingsChanged` で再適用しないとVRChat側にマスクを戻される。
**この経路は実機未確認。アップロード後に真っ先に確認すべき箇所。**

## 4. 自動生成ツール（`BLIND` メニュー）

すべて `Assets/_BLIND/Editor/` にあるエディタ拡張。**実行順序が決まっている。**

| メニュー | 実装 | 役割 |
|---|---|---|
| `BLIND/軽量化/1. メッシュを軽くする` | `BlindMeshReducer.cs` | 重いメッシュを頂点クラスタリングで減量 |
| `BLIND/軽量化/9. 軽量化を元に戻す` | 同上 | 元メッシュに差し戻す（**元は消していないので常に戻せる**） |
| `BLIND/vision/1. サーマル材質を作り直す` | `BlindThermalTable.cs` | 温度別マテリアルを生成 |
| `BLIND/vision/2. 全部屋にサーモ・エコロケを生成` | `BlindVisionBuilder.cs` | **本体**。Default層を走査してThermal/Echo層を作る |
| `BLIND/エコロケ受信機を集め直す` | `EchoReceiverCollector.cs` | 生成した `EchoReceiver` を `EchoEmitter` に登録 |

**正しい実行順**: 軽量化1 → vision1 → vision2 → 受信機を集め直す → **シーン保存**

### 4.1 `BlindVisionBuilder`（一番複雑）

`=== ROOMS ===` 直下の部屋を全部走査（`roomtest` は除外）。各レンダラーについて：

1. **`Classify()`** でオブジェクト名から材質キーを推定（`Wall` `FloorStone` `Metal` `Wood` `Lamp` `Fire` `Body` …）
2. Thermal層: 同じキーのメッシュを**部屋ごとに1個に結合**して1ドローコールに
3. Echo層: `EchoHighlight` マテリアル＋`EchoReceiver` を付ける

**踏んだ罠と対処（全部コード内コメントに理由が書いてある）:**

| 問題 | 対処 |
|---|---|
| 巨大な物（8mのアヒル等）を球で近似したら部屋を塞いだ | `IsBig()` → 実メッシュのまま単体で出す |
| 生成した受信機が全部部屋の原点にいてエコロケが真っ暗だった | `Recenter()` でメッシュを原点合わせ＋Transformを移動 |
| **生成した `EchoReceiver` 245個に `UdonBehaviour` が付いていなかった**（＝アップロードすると全部死ぬ） | 素の `AddComponent` はC#プロキシしか作らない。`UdonSharpEditor.UdonSharpUndo.AddComponent` を使う |
| 内装が全部バウンディングボックスに潰れていた | CPUから読める軽いメッシュは実形状のまま使う。形が意味を持つ物は220三角形の輪郭専用版を作る |
| 汚れデカールが床とZファイティング | `decal/stain/soot` は生成対象から除外 |
| `security_camera` がスキンメッシュだからと人体(34℃)判定 | 名前ホワイトリストで判定 |

### 4.2 UdonSharp の重要な落とし穴（AIが一番踏む）

UdonSharpのコンポーネントは **C#プロキシ + UdonBehaviour の2つで1組**。
`GameObject.AddComponent<EchoReceiver>()` は**プロキシしか作らない**。
エディタ上は正常に見えるのに、**アップロードすると完全に動かない**。必ず：

```csharp
UdonSharpEditor.UdonSharpUndo.AddComponent(go, typeof(EchoReceiver));
// 値を書いた後
UdonSharpEditor.UdonSharpEditorUtility.CopyProxyToUdon(usb);
```

### 4.3 もう一つの落とし穴：モーダルダイアログ

`EditorUtility.DisplayDialog` はモーダル。**自動化から呼ぶとUnityが完全にフリーズする**（実際に固まった）。
`EchoReceiverCollector` はダイアログを出す `CollectAll()` と出さない `Collect()` に分けてある。**ツールからは必ず `Collect()`**。

## 5. サーモ視点の設計（`BlindThermalTable.cs`）

温度は**実際のサーモグラフィの値を基準**にしつつ、「順序と理由は現実どおり、差は読めるところまで開く」方針。
現実の室内は壁も床も17〜19℃に収まってしまい、そのまま入れると画面が一色の紫になるため。

`dim`（減光）が設計の要：

| 帯 | dim | 意図 |
|---|---|---|
| 建物（床15℃/壁18℃/天井21.5℃） | 0.02〜0.03 | **ほぼ黒**。形を伝えるのはエコロケ役の仕事なので、サーモ役に間取りを読ませない |
| 什器（金属16/小物19/木20/布22℃） | 0.05〜0.09 | 手を伸ばす距離で「何かある」と分かる程度 |
| 水 11℃ | 0.20 | 落ちると危ないので例外的に読ませる |
| 熱源（人34/肌36/CRT47/蛍光灯52/**燃える人66**/安定器68/炎95℃） | 1.0 | **サーモ役の道しるべはこれだけ** |

さらに `_Dim` が小さい物ほど**近くでしか見えない**（`_FadeNear` 5m 〜 `_FadeFar` 200m）。
減光だけだと「近寄れば結局全部読める」ので、その穴を距離フェードで塞いでいる。

### ⚠️ Linear色空間の罠
`col *= _Dim` では**体感の明るさが落ちない**（0.05倍しても知覚は26%までしか落ちない）。
シェーダーで `pow(_Dim, 2.2)` に直してある。**表の数字と見え方がずれたらここを疑う。**

### ⚠️ チカチカ（フリッカー）の原因と対処
1. ワールド空間の細かいノイズが1ピクセルより細かくなるとエイリアスで激しくちらつく
   → `ddx/ddy` でピクセルのワールド幅を測り、模様がそれより細かくなる手前で0にフェード（ミップマップと同じ考え方）
2. **時間で動くノイズを入れてはいけない**。VRだと左右の目に別々のノイズが出て立体視が壊れ、酔いの直接原因になる
3. VRChatのアンチエイリアスは**クライアント側設定**。プロジェクトのQualitySettingsはエディタにしか効かない

## 9. AIアシスタントへの作業上の注意

- **検証は目視で済ませない。** これまでのバグ（受信機が原点にいた／UdonBehaviourが無かった／減光が効いていなかった）は全て「エディタ上は正常に見えた」もの。一時カメラでレイヤー別スクリーンショットを撮って中心ピクセルを取る、`transform.position` を実際に出力して比較する、といった方法で数値的に確認すること
- **`EditorUtility.DisplayDialog` を自動化から呼ばない**（Unityがフリーズする）
- **コードのコメントは理由を書く方針**。「何をしているか」ではなく「なぜその値/その手法なのか」。既存コメントのスタイルに合わせること
- **作者はAPIトークンをチャットに貼ったことがある**。キーやトークンの入力・記述はAI側では行わず、必要なら作者本人に依頼すること
- 他メンバーの部屋（room1,2,3,4,5,6,10,14,18）の**見た目を変える改修は事前に確認**を取ること。レイヤー生成と軽量化は承認済み
- ドキュメントは `配置手順.md`（手順書）とこの `引き継ぎ書.md`（現状把握）の2枚構成。手順が変わったら前者、状況が変わったら後者を更新
