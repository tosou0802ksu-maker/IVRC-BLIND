## 1. プロジェクト概要

**BLIND** — VRChat上の3人非対称協力ホラー探索ゲーム。**NYAA2026 Game & Interaction 部門応募予定**（元はIVRC2026メタバース部門向けに作っていた。§0.5参照）。

※リポジトリ名が `IVRC-BLIND` なのは当時の名残。中身の目的は変わっていない。

3人は**同じ部屋にいるのに見えているものが全く違う**。声で伝え合わないと進めない、というのが作品の核。

| 役割 | 見えるもの | 担当する情報 |
|---|---|---|
| **エコロケ** | 音波パルスが当たった面の**輪郭だけ**が0.6秒光る。それ以外は暗闇 | 空間の**形**（壁・段差・通路・什器） |
| **サーモ** | **熱源だけ**が色で見える。建物はほぼ真っ黒 | **危険と生き物**（炎・人・レーザー・配管・水） |
| **過去人** | 照明のある普通の世界。ただし「今そこにある物」の一部が見えない | **意味**（看板・文字・矢印・記憶） |

**設計の背骨**：サーモ役に部屋の「形」を読ませてはいけない。形を伝えるのはエコロケ役の仕事であり、そこが崩れると非対称協力が成立しない。温度表の `dim` 値はこの原則で決まっている。

世界観はリミナルスペース／バックルームズ系。**ここのクオリティには妥協しない**というのが作者の明言した方針。技術的都合で雰囲気を削る提案は歓迎されない。

## 3. 最重要アーキテクチャ：「4つの世界」

**これを理解していない改修は100%壊れる。**

| Layer | 名前 | 誰に見えるか |
|---|---|---|
| 0 | Default | **過去人だけ** |
| 22 | Thermal | **サーモだけ** |
| 23 | Echo | **エコロケだけ** |
| 24 | Memory | 過去人だけ（看板・文字・「かつての壁」） |
| 25 | **NowOnly** | **誰にも見えない**（今日新設） |

各役割のカメラは自分のレイヤーだけを映し、背景は黒。
**同じ壁を3枚、レイヤー違いで重ねて置いている。**

```
Box_Root                     ← 位置と Collider はここに1つだけ
 ├ Vis_Default   (Layer 0)   ← 普通の見た目
 ├ Vis_Echo      (Layer 23)  ← EchoHighlight マテリアル
 └ Vis_Thermal   (Layer 22)  ← Thermal_*.mat
```

この重複を手で置くのは不可能（部屋19・レンダラー数千）なので、**Default層から Thermal層とEcho層を自動生成するツール**がある（§4）。

### Layer 25 `NowOnly` の使い方（今日新設）
「今そこにあるが、過去人には見えない物」を置くレイヤー。

- Default(0) の実体を 25 に移すと、`PlayerVisionController` が過去人のマスクから落とす
- Echo/Thermal の複製は今までどおり生成される（ビルダーは 25 を除外しない）
- **コライダーはそのまま残る** → 見えないのにぶつかる

現在の使用例：room14 のレーザー44個。エコロケにも過去人にも見えず、**サーモ役だけが警告できる**状態。

### Layer 24 `Memory` の裏技（今日追加）
過去人だけに見えるレイヤーなので、**実際には無い壁**を置ける。
`room9/Memory_SealedDoorway_East` が実例：東の開口(2m×3.25m)に壁を重ねてあり、
過去人は行き止まりに見えるが、コライダーが無いので通れる。エコロケ役は開口として見る。

### ⚠️ VRChat実機の落とし穴
シーンの `Camera.cullingMask` を書き換えても**実機では何も起きない**。
`VRC.SDK3.Rendering.VRCCameraSettings.ScreenCamera.CullingMask` を書き換える必要がある。
`PlayerVisionController.cs` は対応済み。`OnVRCCameraSettingsChanged` で再適用しないとVRChatにマスクを戻される。
**この経路は実機未確認。アップロード後に真っ先に確認すべき箇所。**

## 5. サーモ視点の設計（`BlindThermalTable.cs`）

実際のサーモグラフィの値を基準にしつつ「順序と理由は現実どおり、差は読めるところまで開く」方針。
現実の室内は壁も床も17〜19℃に収まり、そのまま入れると画面が一色の紫になるため。

表示レンジ **12〜70℃**、ガンマ0.65。

| 帯 | 温度 | dim | 意図 |
|---|---|---|---|
| 床 15 / 壁 18 / 天井 21.5℃ | | 0.022〜0.034 | **ほぼ黒**。ここを上げるとサーモ役が自力で間取りを読めてしまい、背骨が折れる |
| 金属16 / 小物19 / 木20 / 布22℃ | | 0.075〜0.13 | 「そこに物がある」＝ぶつかる危険の予告。サーモの正当な領分 |
| 水 11℃ | | 0.24 | 落ちると危ないので例外的に読ませる |
| **配管 38℃** | | **0.55** | 今日引き上げた。長い線なので**間取りがある程度読めてしまう副作用がある** |
| 人体34 / 肌36 / CRT47 / 蛍光灯52 / **レーザー62** / 安定器68 / **燃える人66** / 炎95℃ | | 1.0 | サーモ役の道しるべ |

`dim` は距離フェードにも使われる（`_FadeNear` 5m 〜 `_FadeFar` 200m）。減光だけだと「近寄れば読める」ので距離でも塞いでいる。

### 5.1 人体プロファイル（08-24 追加 / 08-26 全面改訂）

人体を一様な温度で塗ると、サーモ視点では**「黄色い人型のシール」**にしか見えない。
実際のサーモグラフィで人が不気味に写るのは体の中に温度の構造があるからで、平面ではなく塊として立ち上がって見える。`ThermalSurface.shader` の `_BodyProfile` 系がこれを作る。

#### 温度分布は「高さ」ではなく「肉の厚み」で決まる

最初の実装は world Y（床からの高さ）を体の軸の代わりに使っていた。立っている人形なら胴・頭・足先が分かれるので一見それらしいが、**現実の人体の温度分布は高さでは決まらない**。

- 横に伸ばした腕は胴と同じ高さなのに、手先は 10℃ 近く低い
- room16 には**寝ている人形も逆立ちしている人形もいる**。高さ基準だとそういう個体が丸ごと一色になる

体表温度を決めているのは**その場所の肉の厚み**。発熱するのは体積で、放熱するのは表面なので、細い所ほど冷える。実測でだいたい：

| 部位 | 厚み | 温度 | 色 |
|---|---|---|---|
| 胴 | 22cm | 36.5℃ | 赤 |
| 腰 | 17cm | 34℃ | 橙 |
| 太もも・上腕 | 13cm | 31.5℃ | 黄 |
| 前腕・脛 | 6cm | 29℃ | 緑 |
| 手・足 | 2cm | 26.5℃ | 水色 |

この並びは体温分布図とそのまま一致する。

#### `BlindBodyThermalBake.cs`（新規）

`vision/2` の中で、人体メッシュの頂点ごとに**法線の逆向きへレイを撃って肉の厚みを測り**、頂点カラー `r` に「芯からの遠さ」として焼き込む。向きにもポーズにも依存しない。

- 焼いたメッシュは `Art/Models/VisionMeshes/*_core*.asset` に保存。**元のインポートアセットには書き込まない**（過去人視点に波及するため）
- `Physics.queriesHitBackfaces = true` を一時的に立てて裏面に当てる。処理は1体 110ms
- 厚みは**格子で2回ならす**。1回だと減面済みメッシュ(1,441頂点)の三角形がそのまま角ばった継ぎ目として出る
- しきい値は絶対値(m)ではなく**全長比**。巨大な腕(8m)も同じ絵になる
- 測れた厚みの **3%〜82% 点**を目盛りの両端に割り当てる（オートレンジ）。100%点に合わせると「胴の中心の一点だけ赤」になる
- **頂点カラー a = 0.5 が「焼き込み済み」の目印。** 頂点カラーを持たないメッシュには GPU が (1,1,1,1) を渡すので、焼けなかった物は自動的に高さ基準に落ちる（room15 の燃えている人はスキンドメッシュなのでこちら）

| プロパティ | Body/Skin の値 | 意味 |
|---|---|---|
| `_BodyProfile` | 1（他は0） | 0 なら完全に無効。壁・床・配管は従来どおり |
| `_BodyCoreness` | 1 | 頂点カラーから芯を読む。0 なら高さ基準 |
| `_BodyPow` | 1.0 | 落ち方の曲線 |
| `_BodyDrop` | 10（Burningは16） | 手足の先の落差(℃) |
| `_BodyMottle` | 0.6 | 汗腺・血管によるまだら |
| `_BodyVein` | 0.7（Burningは4） | 局所的な高温点 |
| `_BodyCoreY`/`_BodySpread` | 1.15 / 0.85 | **高さ基準のときだけ使う**（焼き込みがあれば無視される） |

#### 表示レンジ 25.5〜37.8℃（共通は 12〜70℃）

**ランプのガンマが 0.65 で上を圧縮する**ので、温度を等間隔に置いても色は上に詰まる。
上限を 42℃ に取ると、胴が黄色止まりになって**赤が一度も出ない**（実際そうなった）。
胴(36.5℃)がランプの 0.92＝白飛びが始まる 0.93 の直前、手足先(26.5℃)が 0.20＝青と水色の境に来るよう逆算した幅がこれ。

`_EdgeCool` も人体だけ 0.10 → **0.05** に落としてある。人体は全面が曲面なので、建物と同じ値だと胴のほとんどが斜めに当たって常に1℃低く出て、いちばん熱いはずの胴が赤に届かない。

⚠️ **ここの数字は互いに噛み合っている。** `_TempMin` / `_TempMax` / `_BodyDrop` / ガンマ / `_EdgeCool` のどれか1つだけ動かすと色の並びが崩れる。動かすときは `BlindThermalTable.cs` のコメントにある逆算をやり直すこと。

### 5.2 体温の揺らぎ `ThermalBodyDrift.cs`（08-24 追加）

温度が固定だと人形は「止まった絵」にしかならず、一度見れば以降は情報が増えない。
本物のサーモグラフィが不気味なのは、生きている物の温度が絶えず動くから。

- 対象ごとに違う周期(7〜19秒)と位相で `_HeatIntensity` を揺らす（MaterialPropertyBlock）
- **部屋ごとに1体だけ「暖かい個体」**を選ぶ。他より高温を保ち、違うリズムで脈打つ
  → サーモ役だけが「16体のうち1体だけ体温がある＝どれかが生きている」と読める
- 同期しない（各クライアントがローカル計算）。見た目の揺らぎなので揃える必要が無い
- `BlindVisionBuilder.WireBodyDrift()` が `vision/2` の最後に自動で配線する

**このために人体は結合しない設計にした**（`MakeInstance` の先頭で `standalone = true`）。
結合すると16体が1枚のメッシュになり、MaterialPropertyBlock はレンダラー単位でしか効かないので「16体が完全に同じ呼吸をする」ことしかできない。代償はドローコール +18 程度。
（結合しないことは §5.1 の厚み焼き込みにも都合が良い。結合すると全員が1つの厚み分布に混ざって、オートレンジが体ごとに効かなくなる。）

### 5.25 熱の流れ（配管・配線）`_FlowStrength`（08-27 追加）

配管を一様な温度で塗ると、サーモ役の画面では「線が引いてあるだけ」で建物が止まって見える。
実際の配管は中を通る温水や排気で温度が波打つので、ワールド座標のゆっくりした正弦波を足す。

```hlsl
float3 axis = normalize(float3(1.0, 0.35, 0.6));   // 斜め軸。どの向きの管にも波が乗る
float phase = (dot(i.worldPos, axis) - _Time.y * _FlowSpeed) / _FlowLength;
tempC += sin(phase * 6.2831853) * _FlowStrength;
```

| キー | 温度 | `_FlowStrength` | 意味 |
|---|---|---|---|
| `DuctDead` | 21℃ | **0** | 電気の来ていない線。**動かないことが情報になる** |
| `DuctWarm` | 29℃ | 1.6 | ゆっくり脈打つ |
| `Duct` | 38℃ | 2.6 | 標準の配管 |
| `DuctHot` | 46℃ | 3.4 | 速く強く脈打つ |

⚠️ **時間で動かしてよいのはここだけ。** ノイズ（`NoiseOct` / `NoiseSmooth`）を時間で動かすと
VRで左右の目に別々の粒が出て立体視が壊れる。これはワールド座標のなめらかな正弦波なので
左右の目で完全に同じ値になり、その問題は起きない。

⚠️ **エディタの手動 `cam.Render()` では `_Time.y` が 0 のままなので、動きを確認できない。**
`Shader.SetGlobalVector("_Time", ...)` もエンジンが描画時に上書きするので効かない。
**確認はプレイモードで行うこと。** 実測：`Time.time=24.35` で輝度合計 6361.89 →
`Time.time=53.05` で 6402.47（同一フレーム内の3回は完全に同値＝フレーム単位で更新されている）。

### 5.3 サーモのノイズは2種類ある

`NoiseOct`（マス目ごとに一定）と `NoiseSmooth`（8隅を補間）を使い分けている。

- **センサーの固定パターンノイズ・材質のムラ** → `NoiseOct`。実機のノイズはマス目状で正しい
- **体表の温度ムラ（`_BodyMottle` / `_BodyVein`）** → `NoiseSmooth`。血流と発汗の分布なので境目があってはいけない

最初は体にも `NoiseOct` を使っていて、**8cm角の市松模様が体に浮いて圧縮ノイズのように見えていた**。

⚠️ **どちらも時間で動かしてはいけない。** VRだと左右の目に別々のノイズが出て立体視が壊れ、ちらつきと酔いの直接の原因になる。実機のサーマルのざらつきは「固定パターンノイズ」なので、止まっていても嘘ではない。

### ⚠️ 表示レンジ上限70℃の意味
**70℃を超える温度は全部 h=1.0 に張り付いて同じ真っ白になる。**
レーザーを88℃にしていた時、炎95℃と区別が付かず、さらに画面が白飛びしていた。
**新しい熱源を足すときは必ず70℃以下に収めるか、`DisplayMax` ごと見直すこと。**

### ⚠️ Linear色空間の罠
`col *= _Dim` では体感の明るさが落ちない（0.05倍しても知覚は26%まで）。
シェーダーで `pow(_Dim, 2.2)` に補正済み。**表の数字と見え方がずれたらここを疑う。**

### ⚠️ チカチカ対策（再発させないこと）
1. ワールド空間ノイズが1ピクセルより細かいと激しくちらつく → `ddx/ddy` でピクセルのワールド幅を測りフェード
2. **時間で動くノイズを入れてはいけない。** VRだと左右の目に別のノイズが出て立体視が壊れる
3. VRChatのアンチエイリアスは**クライアント側設定**。プロジェクトのQualitySettingsはエディタにしか効かない

### 9.2 UdonSharp のコンポーネント二重構造
`AddComponent<T>()` は **C#プロキシしか作らない**。エディタ上は正常に見えるのに、**アップロードすると完全に動かない**。

```csharp
UdonSharpEditor.UdonSharpUndo.AddComponent(go, typeof(EchoReceiver));

```

検証は必ず UdonBehaviour 側の値を読むこと：

```csharp
ub.publicVariables.TryGetVariableValue("glowDuration", out object v);
```

### 9.3 `LayerMask` へのビット演算がUdonで落ちる
`mask &= ~(1 << 25)` は `int → LayerMask` の暗黙変換を呼ぶが、**この演算子はUdonに公開されていない**。
`Method is not exposed to Udon` でU#のコンパイルが丸ごと落ち、**その結果シーンが空で読み込まれる**（原因が非常に分かりにくい）。
`LayerMask → int` の向きだけは公開されているので、**最初に int にして以降 int で通すこと**。

### 9.4 `EditorUtility.DisplayDialog` は自動化から呼ぶな
モーダルなのでUnityが完全にフリーズする。ダイアログ版とロジック版を必ず分けること。

### 9.6e エコロケ層を作り直したら受信機を必ず登録し直す（08-26 発生）


⚠️ **エコロケ層はエディタで見ると真っ黒だが、それは正常。**

### 9.6g エコロケがベタ塗りになる原因は2つある（08-27 修正）

「エコロケ視点で床が一面に光って何も読めない」は、原因が**2つ重なっていた**。

**① UVが 0〜1 の外にあった（落とし穴フロア）**
`EchoHighlight` は `min(uv, 1-uv)` でUVの端からの距離を測る。
UVが範囲外だと `min()` が負になり `saturate()` が 0 に潰れて **`edge = 1.0` ＝ 面全体が塗りつぶし**になる。
落とし穴の床は床材のタイリングを揃えるためワールド座標をそのままUVに入れていた（−12〜0）。

→ `BlindGimmickBuilder.Emit()` の echo 分岐で**面（Quad）ごとに 0〜1** を貼るよう修正。
メッシュ全体のバウンズで正規化すると「9.2mの行が1個だけ縁取られる」だけでマス目が読めないので、面単位にすること。

**② `EchoMaterial_Prop` のリムが強すぎた（全部屋）**
`_RimWeight` 0.45 は丸い物（room7のアヒル）の輪郭を出すために入れた値だが、
`_RimPower` が 2.5 と緩く、**浅い角度で見た平らな面が全面光っていた**。
room14 の 8.2m × 3.1m の平板プロップがこれで真っ白になっていた。

→ `_RimPower` を **2.5 → 12** に。リムが本当に縁の部分だけに絞られ、
**丸物のシルエットは残したまま**平面のベタ塗りだけが消える。`_RimWeight` は 0.45 のままでよい。

実測（点灯画素 / うち明るい面）:

| | 修正前 | 修正後 |
|---|---|---|
| room14 | 16.6% / 9.6% | **9.5% / 2.4%** |
| room7  | 21.3% / 3.0% | **2.2% / 1.6%** |
| room4  | ベタ塗り | **3.4% / 1.6%** |
| room9  | ベタ塗り | **5.0% / 2.7%** |

### 9.6h 「輪郭しか描かない視点」では、穴と床が同じ絵になる（08-27）

ベタ塗りを直した直後、**どのマスが穴なのか全く判別できない**という問題が残った。
エコロケはUVの端にしか線を引かないので、**中身の無いマス（穴）と床のマスが
まったく同じ長方形の輪郭**になるため。真上から見ても目線から見ても区別できなかった。

さらに、目線1.6mから5m先の穴を覗き込める深さは約45cmしかない（幾何学的な限界）。
**「深くすれば穴に見える」は近くの穴にしか効かない。**

対策を2つ入れた。

| | 内容 | 効く距離 |
|---|---|---|
| `PitRings = 6` | 縦坑の側面を6段の帯に割る。1段ごとに輪が描かれ、穴の中に等間隔の線が下へ並ぶ | 近く（覗き込んだとき） |
| `PitInset = 0.12` | 縦坑をマスより12cm内側に掘る。穴だけ「二重の四角」になる | **遠くでも** |

`PitDepth` も 3m → 5m にした。**当たり判定はマス全体のままなので、
`PitInset` を変えても落ちる範囲は変わらない**（見た目だけの調整）。

### 9.6i 真犯人：部屋の床がサーモ/エコロケ層にも複製されて穴を塞いでいた（08-27）

上の対策を入れてもサーモ視点に穴が一切出ず、調べたら**別の原因**だった。

穴の中の熱源（`Thermal_PitVoid` 45℃）は正しく作られていたのに、
**その上を部屋のカーペット床の複製（`T_Fabric (22.0C)`）が覆っていた。**
サーモ視点で見えていた「暗いティール色の板」がそれ。

`DisableOriginalFloor()` は Vision_* の子から名前に **`Floor` を含む物**だけを止めていたが、
`BlindVisionBuilder` はサーモ/エコロケ層を**温度キーごとに結合**するので、
カーペット床は `T_Fabric (22.0C)`、石床は `T_FloorStone (15.0C)` という名前になり、
**この名前判定をすり抜けていた。**

→ 名前ではなく**形**で判定するよう修正:

```
薄い(size.y <= 0.5) かつ 上面が床の高さ(-0.60 <= max.y <= 0.35)
かつ 部屋の矩形(rx0..rz1)と重なる  →  床とみなして止める
```

壁は厚みで、天井は高さで除外される。実際に止まったのは
`T_Fabric` / `T_FloorStone` / `E_Floor_*` / 床高さの `E_P0_*` だけで、
背の高いプロップは残った。

**教訓：`BlindVisionBuilder` の生成物を名前で拾う処理は、
温度キーで結合されることを前提にしないと必ず取りこぼす。**

#### 最終的な穴の見え方

| 視点 | 穴の見え方 |
|---|---|
| 過去人 | 従来どおり（床材のまま、穴は暗い） |
| **サーモ** | **明るい黄色の四角**（45℃の熱源に開口のすぐ下で蓋をして、距離に関係なく見える） |
| **エコロケ** | **完全な黒**。踏み板を10cm内側に描いて1マスずつ独立させたので、穴は「タイルが抜けている場所」として読める |

当たり判定の実測：安全マス31点で床にヒット、穴マス29点は落下判定のみ。

### 9.6j 穴の配置が偏り、端を素通りできていた（08-27 修正）

配置を可視化したところ3つの問題があった。

```
修正前 room4            修正前 room14
T ・T T E P             T ・・E ・T
P P ? P P ?  ← 4連続    ・・・P ・T   ← 左2列が
E E E P E E  ← 1行が    ・P P ・T E      ほぼ素通り
・E ・T P P     全部E    ・・E E T P
```

1. **1行がまるごと同じ役**（`E E E P E E`）── その行はその1人が読むだけで越えられ、3人で擦り合わせる必要が消える
2. **同じ役が4連続**（過去人の穴が塊になる）
3. **端の列がまるごと安全** ── 端を歩くだけで抜けられる＝この部屋の存在意義が消える

原因は `Assign()` の2箇所。

| 箇所 | 修正前 | 修正後 |
|---|---|---|
| 安全な道 | 1行ごとに ±1 列ずらすだけ。乱数次第で端に貼り付く | 数行ごとに**左寄り／右寄りの帯を交互に通る折り返し点**を置いて必ず横断させる |
| 役の割り当て | シャッフルして `i % 3`。個数は揃うが場所は運任せ | 置くたびに**周囲2マスを見て、同じ役がいちばん少ない役**を選ぶ（距離に反比例した penalty） |

さらに **「穴がゼロの列を作らない」保証**を追加した。密度の低い部屋では上の2つを直しても
端の列が空くことがあるため、列ごとに最低1つ穴があることを乱数に頼らず保証する。
このとき**安全な道から最も離れたマス**を選ぶ（道のすぐ隣を塞ぐと理不尽になるため）。

単調さ対策として密度を部屋ごとに変えた：room4=0.55（入門）/ room14=0.70 / room9=0.80（最難）。

#### 修正後の実測

| | 素通りできる列 | 同じ役の最大連続 | 入口→出口 |
|---|---|---|---|
| room4 | なし ✓ | 2 ✓ | 到達可能 ✓ |
| room9 | なし ✓ | 2 ✓ | 到達可能 ✓ |
| room14 | なし ✓ | 2 ✓ | 到達可能 ✓ |

⚠️ **配置を変えたら必ず「入口→出口が4方向でつながっているか」を物理判定で確認すること。**
穴を増やす方向の変更は、簡単に「物理的に渡れない部屋」を作ってしまう。

**追記（08-27 その2）：行の保証と、扉を塞ぐ指定を足した。**

- 列だけ保証しても**行がまるごと安全**だと横に素通りできる。room4 の出口の行が6マス中5マス安全だった。
  → 行にも「最低1つは穴」を保証。全部屋で穴ゼロの行・列ともに 0 になった。
- `PitSpec` に `bx0..bz1`（ワールド矩形）を追加。**その中は確率を通さず必ず穴**にし、
  安全な道もそこへ入らないよう列を外へ押し出す（`PushOutOfBlock`）。
  room9 では room8 への西の開口（x=-9.1 / z=-46.0〜-44.4）に指定して、
  room9 側からは渡れなくした（フィールドを z=-42.0 → -46.8 まで南へ延長）。
  **room8 は room7 との北の開口（z=-40.7 / x≈-19.2）から入れるので孤立しない**
  ── 塞ぐ前に必ず「その部屋に別の入口があるか」をレイキャストで確認すること。

### 9.6k 配管を箱にすると視界が全部埋まる（08-27 修正）

room10 の配線束は**1個 72,024 三角形**あり、`MaxPropTris`(180) を大きく超えるので
バウンディングボックス（2.5×1.3×2.9m の**中身の詰まった箱**）に置き換えられていた。
それが19個ぶん天井に並び、**サーモ視点の 74% が巨大な板で埋まっていた。**

`IsThinAndLong()` は「細くて長い物」しか除外しないので、
**絡まった配線の束（ずんぐりしたバウンズ）はすり抜けてしまう。**

→ `MakeInstance` に `IsDuctKey()` の分岐を追加し、配管・配線は箱にせず
`BlindMeshReducer.SaveLite` で減面する（`DuctShapeTris = 1200`）。
実測：サーモ 74.4% → 36.8%、天井が配線の網として読めるようになった。
room10 のサーモは 96,763 三角形（うち配管 88,369）。エコロケ側には配管が入らないので
形の情報が汚れていない。

⚠️ **`Classify()` の「配線を4段階に散らす」判定は部屋名で分岐している。**
部屋番号の振り直し（§1.5）で対象が room11 → **room10** に変わっていたため、
一時的に全部 `Duct`(38℃) 一色になっていた。**部屋名で分岐する処理は番号変更に弱い。**

### 9.6 簡易形状（箱）の落とし穴
バウンディングボックスで代用するので、
- **斜めに走る細い物**（レーザー・パイプ）は実体の何十倍もの板になる → `IsThinAndLong()` で除外
- **巨大な物**（8mのアヒル）は部屋を塞ぐ → `IsBig()` で除外
- **人体**を箱にすると「人の形」という情報が消える → `Body/Skin/Burning` は300三角形に粗くしてでも実形状

### 9.7 検証は目視で済ませない
これまでのバグは全て「エディタ上は正常に見えた」もの。
一時カメラでレイヤー別スクリーンショットを撮り、中心ピクセルを数値で比較する。
オブジェクトを1つずつ無効化して輝度の変化を見る二分探索が有効（`t_room14` の白飛び特定はこれで解決した）。

**注意**：エコロケの検証で全受信機の `_GlowIntensity` を1にすると**マップ全体が光る**ので、遠くの部屋まで写って誤診する。実機では12m以内しか光らない。

## 13. チームメンバーからの引き継ぎ指示（2026-08-21付、実装状況を追記）

以下は08-21深夜時点でチームメンバーが残した指示。**大部分は実装済み**（§7.5参照）。指示原文はそのまま残し、実装状況を各項目に追記した。

### 落とし穴と普通の穴への付与
- **普通の穴**: 床に当たり判定をなくして、エコロケは与えない。
- **落とし穴**: 床に当たり判定をなくして、エコロケを与えて、サーモを渡す。

→ **実装済み**（`PitField_Generated`、room5/10/18）。ただし実装したロジックは上記の「普通の穴／落とし穴」の区別ではなく、**役職ごとに異なるマスを穴にする**（過去人だけの穴・サーモだけの穴・エコロケだけの穴を1つの穴フィールド内に混在させる）方式になっている。指示の意図と食い違っている可能性があるので、本人に「これで良いか」を確認すること。食い違っていれば `BlindGimmickBuilder.cs` の `Assign()` を書き換える。

### クイズとドア
ドアを全部閉めた状態にしてから、ゲームマネージャーとドアとリスポン地点に付与する。問題文と選択肢の貼り付け。
- **DoorQuizChoice**（ドア1枚ごとに付ける）
  - プレイヤーがInteractしたら、自分の番号を `DoorQuizManager` に送る。
  - `doorQuizManager` — このドアが属する `DoorQuizManager` をドラッグ
  - `doorIndex` — このドアの番号（0, 1, 2）
- **DoorQuizManager**（1問につき1つ配置）
  - 選択されたドア番号と正解を比較し、正解→ドアを移動、不正解→全員チェックポイントへ戻す。
  - `correctDoorIndex` — 正解のドア番号（0, 1, 2）
  - `door0` / `door1` / `door2` — 3枚のドアのTransformをドラッグ
  - `door0OpenPosition` / `door1OpenPosition` / `door2OpenPosition` — ドアの開いた位置のVector3（正解ドアのみ実際に使用される）
  - `checkpointManager` — シーン内の `CheckpointManager` をドラッグ
  - `correctSound` / `wrongSound` — 正解時・不正解時の音（任意）

→ **`QuizManager1/2/3` として3問配置済み**（room13ほか）。ただし **`checkpointManager` が空の方の `CheckpointManager` を指していて機能していない**（§7.5の致命的バグ）。`correctDoorIndex` が3問とも0固定、不正解側の open position がプレースホルダのまま、`correctSound`/`wrongSound` 未設定、問題文UIが見当たらない、という点も未解決。**`DoorQuizChoice` が各ドアに付いているかは未確認**（本節作成時はシーン内で `DoorQuizChoice` のスクリプト参照を見つけられなかった）。

### 各種ドアとボタン（対応するドアとボタンにコンポーネント付与）
- **MultiButtonDoor**
  - GameObjectにアタッチする。複数のボタンがインタラクトされてand回路でドアを開閉する。
  - 移動させるドアとドアの開閉時の座標を設定できる。開閉時の効果音も設定できる。
- **MultiButtonDoorButton**
  - ボタンにアタッチする。ボタンIDで重複を避ける。ボタン押した時の効果音を設定できる。
- **SingleButtonDoor** / **SingleButtonDoorButton** / **SingleButtonDualDoor** / **SingleButtonDualDoorButton**

→ **`MultiButtonDoor` はroom3のシャッターに実装済み**。ただし専用の `MultiButtonDoorButton` ではなく、赤/青/緑の見た目とチェックポイント登録を兼ねる `ColorGateButton`（新規スクリプト）をボタン側に使っている。`SingleButtonDoor` 系は**シーン内に一つも使用箇所が無い**（§7.5）。

### 感圧板とドア（対応するドアと感圧板にコンポーネント付与）
- **DualPressurePlateDoor** / **DualPressurePlate**

→ **未使用**（§7.5）。手つかずのまま。

### CheckpointManager（シーンに1つ）
不正解時などに `TriggerDeath()` が呼ばれ、全員を現在のセーブポイントにテレポートさせる。
- `checkpoints` — Transform配列。[0] はスタート地点（復帰先、空のGameObject）。[1] 以降は各セーブポイント。
- `doors` — 進行で開閉するToggleDoor（なければ空）
- `deathEffect` / `deathSound` — 死亡演出・音（任意）

→ **「シーンに1つ」のはずが実際は2つ存在し、参照が割れている。これが現状最大のバグ（§7.5）。** `checkpoints` 配列は正しい方には4地点(`CP_0_Start`〜`CP_3_Green`)入っている。`doors` は今のところどちらの `CheckpointManager` にも設定されていない（room3シャッターの開閉はチェックポイントではなくボタン3個の同時押しで駆動しているため、`ToggleDoor` 経由の連動は現状未使用）。`deathEffect` / `deathSound` も未設定。
