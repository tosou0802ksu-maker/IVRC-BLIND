## 1. プロジェクト概要

**BLIND** — VRChat上の3人非対称協力ホラー探索ゲーム。**NYAA2026 Game & Interaction 部門応募予定**（元はIVRC2026メタバース部門向けに作っていた。§0.5参照）。

※リポジトリ名が `IVRC-BLIND` なのは当時の名残。中身の目的は変わっていない。

3人は**同じ部屋にいるのに見えているものが全く違う**。声で伝え合わないと進めない、というのが作品の核。

| 役割 | 見えるもの | 担当する情報 |
|---|---|---|
| **エコロケ** | 音波パルスが当たった面の**輪郭だけ**が0.6秒光る。それ以外は暗闇 | 空間の**形**（壁・段差・通路・什器） |
| **サーモ** | **熱源だけ**が色で見える。建物はほぼ真っ黒 | **危険と生き物**（炎・人・レーザー・配管・水） |
| **過去人** | 照明のある普通の世界。ただし「今そこにある物」の一部が見えない | **意味**（看板・文字・矢印・記憶） |

**設計の背骨**：サーモ役に部屋の「形」を読ませてはいけない。形を伝えるのはエコロケ役の仕事であり、そこが崩れると非対称協力が成立しない。温度表の `dim` 値はこの原則で決まっている。

世界観はリミナルスペース／バックルームズ系。**ここのクオリティには妥協しない**というのが作者の明言した方針。技術的都合で雰囲気を削る提案は歓迎されない。

## 3. 最重要アーキテクチャ：「4つの世界」

**これを理解していない改修は100%壊れる。**

| Layer | 名前 | 誰に見えるか |
|---|---|---|
| 0 | Default | **過去人だけ** |
| 22 | Thermal | **サーモだけ** |
| 23 | Echo | **エコロケだけ** |
| 24 | Memory | 過去人だけ（看板・文字・「かつての壁」） |
| 25 | **NowOnly** | **誰にも見えない**（今日新設） |

各役割のカメラは自分のレイヤーだけを映し、背景は黒。
**同じ壁を3枚、レイヤー違いで重ねて置いている。**

```
Box_Root                     ← 位置と Collider はここに1つだけ
 ├ Vis_Default   (Layer 0)   ← 普通の見た目
 ├ Vis_Echo      (Layer 23)  ← EchoHighlight マテリアル
 └ Vis_Thermal   (Layer 22)  ← Thermal_*.mat
```

この重複を手で置くのは不可能（部屋19・レンダラー数千）なので、**Default層から Thermal層とEcho層を自動生成するツール**がある（§4）。

### Layer 25 `NowOnly` の使い方（今日新設）
「今そこにあるが、過去人には見えない物」を置くレイヤー。

- Default(0) の実体を 25 に移すと、`PlayerVisionController` が過去人のマスクから落とす
- Echo/Thermal の複製は今までどおり生成される（ビルダーは 25 を除外しない）
- **コライダーはそのまま残る** → 見えないのにぶつかる

現在の使用例：room14 のレーザー44個。エコロケにも過去人にも見えず、**サーモ役だけが警告できる**状態。

### Layer 24 `Memory` の裏技（今日追加）
過去人だけに見えるレイヤーなので、**実際には無い壁**を置ける。
`room9/Memory_SealedDoorway_East` が実例：東の開口(2m×3.25m)に壁を重ねてあり、
過去人は行き止まりに見えるが、コライダーが無いので通れる。エコロケ役は開口として見る。

### ⚠️ VRChat実機の落とし穴
シーンの `Camera.cullingMask` を書き換えても**実機では何も起きない**。
`VRC.SDK3.Rendering.VRCCameraSettings.ScreenCamera.CullingMask` を書き換える必要がある。
`PlayerVisionController.cs` は対応済み。`OnVRCCameraSettingsChanged` で再適用しないとVRChatにマスクを戻される。
**この経路は実機未確認。アップロード後に真っ先に確認すべき箇所。**

## 5. サーモ視点の設計（`BlindThermalTable.cs`）

実際のサーモグラフィの値を基準にしつつ「順序と理由は現実どおり、差は読めるところまで開く」方針。
現実の室内は壁も床も17〜19℃に収まり、そのまま入れると画面が一色の紫になるため。

表示レンジ **12〜70℃**、ガンマ0.65。

| 帯 | 温度 | dim | 意図 |
|---|---|---|---|
| 床 15 / 壁 18 / 天井 21.5℃ | | 0.022〜0.034 | **ほぼ黒**。ここを上げるとサーモ役が自力で間取りを読めてしまい、背骨が折れる |
| 金属16 / 小物19 / 木20 / 布22℃ | | 0.075〜0.13 | 「そこに物がある」＝ぶつかる危険の予告。サーモの正当な領分 |
| 水 11℃ | | 0.24 | 落ちると危ないので例外的に読ませる |
| **配管 38℃** | | **0.55** | 今日引き上げた。長い線なので**間取りがある程度読めてしまう副作用がある** |
| 人体34 / 肌36 / CRT47 / 蛍光灯52 / **レーザー62** / 安定器68 / **燃える人66** / 炎95℃ | | 1.0 | サーモ役の道しるべ |

`dim` は距離フェードにも使われる（`_FadeNear` 5m 〜 `_FadeFar` 200m）。減光だけだと「近寄れば読める」ので距離でも塞いでいる。

### 5.1 人体プロファイル（08-24 追加 / 08-26 全面改訂）

人体を一様な温度で塗ると、サーモ視点では**「黄色い人型のシール」**にしか見えない。
実際のサーモグラフィで人が不気味に写るのは体の中に温度の構造があるからで、平面ではなく塊として立ち上がって見える。`ThermalSurface.shader` の `_BodyProfile` 系がこれを作る。

#### 温度分布は「高さ」ではなく「肉の厚み」で決まる

最初の実装は world Y（床からの高さ）を体の軸の代わりに使っていた。立っている人形なら胴・頭・足先が分かれるので一見それらしいが、**現実の人体の温度分布は高さでは決まらない**。

- 横に伸ばした腕は胴と同じ高さなのに、手先は 10℃ 近く低い
- room16 には**寝ている人形も逆立ちしている人形もいる**。高さ基準だとそういう個体が丸ごと一色になる

体表温度を決めているのは**その場所の肉の厚み**。発熱するのは体積で、放熱するのは表面なので、細い所ほど冷える。実測でだいたい：

| 部位 | 厚み | 温度 | 色 |
|---|---|---|---|
| 胴 | 22cm | 36.5℃ | 赤 |
| 腰 | 17cm | 34℃ | 橙 |
| 太もも・上腕 | 13cm | 31.5℃ | 黄 |
| 前腕・脛 | 6cm | 29℃ | 緑 |
| 手・足 | 2cm | 26.5℃ | 水色 |

この並びは体温分布図とそのまま一致する。

#### `BlindBodyThermalBake.cs`（新規）

`vision/2` の中で、人体メッシュの頂点ごとに**法線の逆向きへレイを撃って肉の厚みを測り**、頂点カラー `r` に「芯からの遠さ」として焼き込む。向きにもポーズにも依存しない。

- 焼いたメッシュは `Art/Models/VisionMeshes/*_core*.asset` に保存。**元のインポートアセットには書き込まない**（過去人視点に波及するため）
- `Physics.queriesHitBackfaces = true` を一時的に立てて裏面に当てる。処理は1体 110ms
- 厚みは**格子で2回ならす**。1回だと減面済みメッシュ(1,441頂点)の三角形がそのまま角ばった継ぎ目として出る
- しきい値は絶対値(m)ではなく**全長比**。巨大な腕(8m)も同じ絵になる
- 測れた厚みの **3%〜82% 点**を目盛りの両端に割り当てる（オートレンジ）。100%点に合わせると「胴の中心の一点だけ赤」になる
- **頂点カラー a = 0.5 が「焼き込み済み」の目印。** 頂点カラーを持たないメッシュには GPU が (1,1,1,1) を渡すので、焼けなかった物は自動的に高さ基準に落ちる（room15 の燃えている人はスキンドメッシュなのでこちら）

| プロパティ | Body/Skin の値 | 意味 |
|---|---|---|
| `_BodyProfile` | 1（他は0） | 0 なら完全に無効。壁・床・配管は従来どおり |
| `_BodyCoreness` | 1 | 頂点カラーから芯を読む。0 なら高さ基準 |
| `_BodyPow` | 1.0 | 落ち方の曲線 |
| `_BodyDrop` | 10（Burningは16） | 手足の先の落差(℃) |
| `_BodyMottle` | 0.6 | 汗腺・血管によるまだら |
| `_BodyVein` | 0.7（Burningは4） | 局所的な高温点 |
| `_BodyCoreY`/`_BodySpread` | 1.15 / 0.85 | **高さ基準のときだけ使う**（焼き込みがあれば無視される） |

#### 表示レンジ 25.5〜37.8℃（共通は 12〜70℃）

**ランプのガンマが 0.65 で上を圧縮する**ので、温度を等間隔に置いても色は上に詰まる。
上限を 42℃ に取ると、胴が黄色止まりになって**赤が一度も出ない**（実際そうなった）。
胴(36.5℃)がランプの 0.92＝白飛びが始まる 0.93 の直前、手足先(26.5℃)が 0.20＝青と水色の境に来るよう逆算した幅がこれ。

`_EdgeCool` も人体だけ 0.10 → **0.05** に落としてある。人体は全面が曲面なので、建物と同じ値だと胴のほとんどが斜めに当たって常に1℃低く出て、いちばん熱いはずの胴が赤に届かない。

⚠️ **ここの数字は互いに噛み合っている。** `_TempMin` / `_TempMax` / `_BodyDrop` / ガンマ / `_EdgeCool` のどれか1つだけ動かすと色の並びが崩れる。動かすときは `BlindThermalTable.cs` のコメントにある逆算をやり直すこと。

### 5.2 体温の揺らぎ `ThermalBodyDrift.cs`（08-24 追加）

温度が固定だと人形は「止まった絵」にしかならず、一度見れば以降は情報が増えない。
本物のサーモグラフィが不気味なのは、生きている物の温度が絶えず動くから。

- 対象ごとに違う周期(7〜19秒)と位相で `_HeatIntensity` を揺らす（MaterialPropertyBlock）
- **部屋ごとに1体だけ「暖かい個体」**を選ぶ。他より高温を保ち、違うリズムで脈打つ
  → サーモ役だけが「16体のうち1体だけ体温がある＝どれかが生きている」と読める
- 同期しない（各クライアントがローカル計算）。見た目の揺らぎなので揃える必要が無い
- `BlindVisionBuilder.WireBodyDrift()` が `vision/2` の最後に自動で配線する

**このために人体は結合しない設計にした**（`MakeInstance` の先頭で `standalone = true`）。
結合すると16体が1枚のメッシュになり、MaterialPropertyBlock はレンダラー単位でしか効かないので「16体が完全に同じ呼吸をする」ことしかできない。代償はドローコール +18 程度。
（結合しないことは §5.1 の厚み焼き込みにも都合が良い。結合すると全員が1つの厚み分布に混ざって、オートレンジが体ごとに効かなくなる。）

### 5.25 熱の流れ（配管・配線）`_FlowStrength`（08-27 追加）

配管を一様な温度で塗ると、サーモ役の画面では「線が引いてあるだけ」で建物が止まって見える。
実際の配管は中を通る温水や排気で温度が波打つので、ワールド座標のゆっくりした正弦波を足す。

```hlsl
float3 axis = normalize(float3(1.0, 0.35, 0.6));   // 斜め軸。どの向きの管にも波が乗る
float phase = (dot(i.worldPos, axis) - _Time.y * _FlowSpeed) / _FlowLength;
tempC += sin(phase * 6.2831853) * _FlowStrength;
```

| キー | 温度 | `_FlowStrength` | 意味 |
|---|---|---|---|
| `DuctDead` | 21℃ | **0** | 電気の来ていない線。**動かないことが情報になる** |
| `DuctWarm` | 29℃ | 1.6 | ゆっくり脈打つ |
| `Duct` | 38℃ | 2.6 | 標準の配管 |
| `DuctHot` | 46℃ | 3.4 | 速く強く脈打つ |

⚠️ **時間で動かしてよいのはここだけ。** ノイズ（`NoiseOct` / `NoiseSmooth`）を時間で動かすと
VRで左右の目に別々の粒が出て立体視が壊れる。これはワールド座標のなめらかな正弦波なので
左右の目で完全に同じ値になり、その問題は起きない。

⚠️ **エディタの手動 `cam.Render()` では `_Time.y` が 0 のままなので、動きを確認できない。**
`Shader.SetGlobalVector("_Time", ...)` もエンジンが描画時に上書きするので効かない。
**確認はプレイモードで行うこと。** 実測：`Time.time=24.35` で輝度合計 6361.89 →
`Time.time=53.05` で 6402.47（同一フレーム内の3回は完全に同値＝フレーム単位で更新されている）。

### 5.3 サーモのノイズは2種類ある

`NoiseOct`（マス目ごとに一定）と `NoiseSmooth`（8隅を補間）を使い分けている。

- **センサーの固定パターンノイズ・材質のムラ** → `NoiseOct`。実機のノイズはマス目状で正しい
- **体表の温度ムラ（`_BodyMottle` / `_BodyVein`）** → `NoiseSmooth`。血流と発汗の分布なので境目があってはいけない

最初は体にも `NoiseOct` を使っていて、**8cm角の市松模様が体に浮いて圧縮ノイズのように見えていた**。

⚠️ **どちらも時間で動かしてはいけない。** VRだと左右の目に別々のノイズが出て立体視が壊れ、ちらつきと酔いの直接の原因になる。実機のサーマルのざらつきは「固定パターンノイズ」なので、止まっていても嘘ではない。

### ⚠️ 表示レンジ上限70℃の意味
**70℃を超える温度は全部 h=1.0 に張り付いて同じ真っ白になる。**
レーザーを88℃にしていた時、炎95℃と区別が付かず、さらに画面が白飛びしていた。
**新しい熱源を足すときは必ず70℃以下に収めるか、`DisplayMax` ごと見直すこと。**

### ⚠️ Linear色空間の罠
`col *= _Dim` では体感の明るさが落ちない（0.05倍しても知覚は26%まで）。
シェーダーで `pow(_Dim, 2.2)` に補正済み。**表の数字と見え方がずれたらここを疑う。**

### ⚠️ チカチカ対策（再発させないこと）
1. ワールド空間ノイズが1ピクセルより細かいと激しくちらつく → `ddx/ddy` でピクセルのワールド幅を測りフェード
2. **時間で動くノイズを入れてはいけない。** VRだと左右の目に別のノイズが出て立体視が壊れる
3. VRChatのアンチエイリアスは**クライアント側設定**。プロジェクトのQualitySettingsはエディタにしか効かない

### 9.2 UdonSharp のコンポーネント二重構造
`AddComponent<T>()` は **C#プロキシしか作らない**。エディタ上は正常に見えるのに、**アップロードすると完全に動かない**。

```csharp
UdonSharpEditor.UdonSharpUndo.AddComponent(go, typeof(EchoReceiver));

```

検証は必ず UdonBehaviour 側の値を読むこと：

ub.publicVariables.TryGetVariableValue("glowDuration", out object v);

### 9.3 `LayerMask` へのビット演算がUdonで落ちる
`mask &= ~(1 << 25)` は `int → LayerMask` の暗黙変換を呼ぶが、**この演算子はUdonに公開されていない**。
`Method is not exposed to Udon` でU#のコンパイルが丸ごと落ち、**その結果シーンが空で読み込まれる**（原因が非常に分かりにくい）。
`LayerMask → int` の向きだけは公開されているので、**最初に int にして以降 int で通すこと**。

### 9.6g エコロケがベタ塗りになる原因は2つある（08-27 修正）

「エコロケ視点で床が一面に光って何も読めない」は、原因が**2つ重なっていた**。

**① UVが 0〜1 の外にあった（落とし穴フロア）**
`EchoHighlight` は `min(uv, 1-uv)` でUVの端からの距離を測る。
UVが範囲外だと `min()` が負になり `saturate()` が 0 に潰れて **`edge = 1.0` ＝ 面全体が塗りつぶし**になる。
落とし穴の床は床材のタイリングを揃えるためワールド座標をそのままUVに入れていた（−12〜0）。

→ `BlindGimmickBuilder.Emit()` の echo 分岐で**面（Quad）ごとに 0〜1** を貼るよう修正。
メッシュ全体のバウンズで正規化すると「9.2mの行が1個だけ縁取られる」だけでマス目が読めないので、面単位にすること。

**② `EchoMaterial_Prop` のリムが強すぎた（全部屋）**
`_RimWeight` 0.45 は丸い物（room7のアヒル）の輪郭を出すために入れた値だが、
`_RimPower` が 2.5 と緩く、**浅い角度で見た平らな面が全面光っていた**。
room14 の 8.2m × 3.1m の平板プロップがこれで真っ白になっていた。

→ `_RimPower` を **2.5 → 12** に。リムが本当に縁の部分だけに絞られ、
**丸物のシルエットは残したまま**平面のベタ塗りだけが消える。`_RimWeight` は 0.45 のままでよい。

実測（点灯画素 / うち明るい面）:

| | 修正前 | 修正後 |
|---|---|---|
| room14 | 16.6% / 9.6% | **9.5% / 2.4%** |
| room7  | 21.3% / 3.0% | **2.2% / 1.6%** |
| room4  | ベタ塗り | **3.4% / 1.6%** |
| room9  | ベタ塗り | **5.0% / 2.7%** |

### 9.6h 「輪郭しか描かない視点」では、穴と床が同じ絵になる（08-27）

ベタ塗りを直した直後、**どのマスが穴なのか全く判別できない**という問題が残った。

さらに、目線1.6mから5m先の穴を覗き込める深さは約45cmしかない（幾何学的な限界）。

対策を2つ入れた。

### 9.6i 真犯人：部屋の床がサーモ/エコロケ層にも複製されて穴を塞いでいた（08-27）

`BlindVisionBuilder` はサーモ/エコロケ層を**温度キーごとに結合**するので、

```

かつ 部屋の矩形(rx0..rz1)と重なる  →  床とみなして止める
```

壁は厚みで、天井は高さで除外される。実際に止まったのは
`T_Fabric` / `T_FloorStone` / `E_Floor_*` / 床高さの `E_P0_*` だけで、
背の高いプロップは残った。

**教訓：`BlindVisionBuilder` の生成物を名前で拾う処理は、
温度キーで結合されることを前提にしないと必ず取りこぼす。**

### 9.6j 穴の配置が偏り、端を素通りできていた（08-27 修正）

配置を可視化したところ3つの問題があった。

```
修正前 room4            修正前 room14
T ・T T E P             T ・・E ・T
P P ? P P ?  ← 4連続    ・・・P ・T   ← 左2列が
E E E P E E  ← 1行が    ・P P ・T E      ほぼ素通り
・E ・T P P     全部E    ・・E E T P
```

1. **1行がまるごと同じ役**（`E E E P E E`）── その行はその1人が読むだけで越えられ、3人で擦り合わせる必要が消える
2. **同じ役が4連続**（過去人の穴が塊になる）
3. **端の列がまるごと安全** ── 端を歩くだけで抜けられる＝この部屋の存在意義が消える

原因は `Assign()` の2箇所。

| 箇所 | 修正前 | 修正後 |
|---|---|---|
| 安全な道 | 1行ごとに ±1 列ずらすだけ。乱数次第で端に貼り付く | 数行ごとに**左寄り／右寄りの帯を交互に通る折り返し点**を置いて必ず横断させる |
| 役の割り当て | シャッフルして `i % 3`。個数は揃うが場所は運任せ | 置くたびに**周囲2マスを見て、同じ役がいちばん少ない役**を選ぶ（距離に反比例した penalty） |

さらに **「穴がゼロの列を作らない」保証**を追加した。密度の低い部屋では上の2つを直しても
端の列が空くことがあるため、列ごとに最低1つ穴があることを乱数に頼らず保証する。
このとき**安全な道から最も離れたマス**を選ぶ（道のすぐ隣を塞ぐと理不尽になるため）。

単調さ対策として密度を部屋ごとに変えた：room4=0.55（入門）/ room14=0.70 / room9=0.80（最難）。

#### 修正後の実測

| | 素通りできる列 | 同じ役の最大連続 | 入口→出口 |
|---|---|---|---|
| room4 | なし ✓ | 2 ✓ | 到達可能 ✓ |
| room9 | なし ✓ | 2 ✓ | 到達可能 ✓ |
| room14 | なし ✓ | 2 ✓ | 到達可能 ✓ |

⚠️ **配置を変えたら必ず「入口→出口が4方向でつながっているか」を物理判定で確認すること。**
穴を増やす方向の変更は、簡単に「物理的に渡れない部屋」を作ってしまう。

**追記（08-27 その2）：行の保証と、扉を塞ぐ指定を足した。**

- 列だけ保証しても**行がまるごと安全**だと横に素通りできる。room4 の出口の行が6マス中5マス安全だった。
  → 行にも「最低1つは穴」を保証。全部屋で穴ゼロの行・列ともに 0 になった。
- `PitSpec` に `bx0..bz1`（ワールド矩形）を追加。**その中は確率を通さず必ず穴**にし、
  安全な道もそこへ入らないよう列を外へ押し出す（`PushOutOfBlock`）。
  room9 では room8 への西の開口（x=-9.1 / z=-46.0〜-44.4）に指定して、
  room9 側からは渡れなくした（フィールドを z=-42.0 → -46.8 まで南へ延長）。
  **room8 は room7 との北の開口（z=-40.7 / x≈-19.2）から入れるので孤立しない**
  ── 塞ぐ前に必ず「その部屋に別の入口があるか」をレイキャストで確認すること。

### 9.6m エコロケの床板がプールを埋めていた（08-28 修正）

エコロケの床は `BoxProxy` をブロック大に引き伸ばした**一枚板**で、
元の床メッシュの形を見ていない。room6（アヒル部屋）のプールは

切り抜いただけでは「暗闇」と区別が付かないので、`BuildHoleRimMesh()` で

⚠️ **穴の形を矩形で近似してはいけない。** 最初バウンズの矩形で抜いたら、
プールの縁は有機的な曲線なので**実際には床がある所まで消え、縁の線も
本物のふちから数メートルずれた所に出た。**

⚠️ **「穴＝閉じた輪」だと思ってはいけない。** room6 のプールは部屋の隅まで達していて、

外周とプールが繋がった1本しか出てこない（実際にそうなった）。

あわせて `EchoMatFor` のシルエット発光を大きさで分けた。
数メートルを超える物に `_RimPower` 3.5 を掛けると寝ている面が全部光って
**ベタ塗りの塊**になり、プールの内壁と巨大アヒルがそうなっていた。
5m超は `_RimPower` 9 にして、本当に縁の所だけ光らせる。

### 9.6p room9 を「渡れない帯」で断ち切る（08-29 改修）

### 9.6q サーモが黄色一色だった（08-29 修正）

### 9.6t 落とし穴部屋を「声の掛け合い」から設計し直す（08-29）

**この部屋の主役は落とし穴ではなく、3人の声の掛け合い。** 穴の数や見た目より、
「喋らないと進めない」が成立しているかを設計の基準にする。

黙って進めてしまう抜け道は2つある。

1. **道の隣が全部安全な行** … その行は誰にも訊かずに歩ける
2. **1人だけが喋り続ける** … 他の2人が置物になる

`Assign()` の手順5.5 で両方を潰した。

- 各行に**必ず1つ、安全な道の真横に穴を置く**。横に動くには誰かに訊くしかない
- その穴の担当を**行ごとに 過去人 → サーモ → エコロケ と回す**。
  答える人が一歩ごとに入れ替わる。始まりの役は `seed` で部屋ごとにずらす

実測（入口→出口の順に、その行で情報を持っている役）:

| 部屋 | 喋る人の並び | 誰の情報も要らない行 |
|---|---|---|
| room4 | 過エ → サエ → 過エ → 過 | **0** |
| room9 | 過エ → 過サ → サ → サエ → 過サ → 過サ → エ → 過 → 過サ → エ → 過サ | **0** |
| room14 | 過サ → 過エ → 過 → サ → エ → 過 → サエ | **0** |

1つしか役が出ていない行（room9 の「サ」「エ」「過」など）は、
**その人が黙ると誰も渡れない**行。room9 には4か所ある。

⚠️ 手順5.5 で決めたマスは `locked` にして、手順6（同じ役だけの行を崩す処理）が
動かさないようにしてある。ここを動かすと喋る順番が崩れる。

**部屋をまたぐ動線にも同じ考えを入れている。**
room9 を断ち切る帯の手前に立っている看板は、**文字なので過去人にしか読めない**
（サーモでは一様な温度の板、エコロケでは輪郭だけ）。
迂回路を知っているのは過去人だけなので、口で伝えるしかない。

### 9.6r サーモの穴の見せ方（08-29）

**開口に蓋（水平な板）は張らない。穴の中そのものに熱を持たせて深さを見せる。**

| 部位 | 位置 | 温度 | 色 |
|---|---|---|---|
| 立ち上がり | 床から **+0.07m**（上面は 3cm だけ） | `PitRim` 14℃ | 水色 |
| 上の内壁 | 0 〜 -0.40m・**垂直・口いっぱい** | `PitRim` 14℃ | 水色 |
| 中ほどの内壁 | -0.40 〜 -1.60m | `PitWall` 7℃ | 青 |
| 深部と底 | -1.60m 〜 底 | `PitVoid` 1℃ | 濃い青紫 |

近づくと 水色→青→濃紫 と輪が重なって見え、それ自体が深さになる。

**⚠️ 開口に水平・準水平な面を一切置かないこと。すり鉢もダメ。**
幅0.40mのすり鉢を付けたことがあるが、1.47mのマスに対して両側0.40m ＝
**開口面積の73%が水平な輪**になり、遠目には水色の板が1枚張ってあるように
しか見えなかった（＝また「蓋」）。深さは水平面ではなく**垂直な内壁の段**で見せる。
開口を内側に狭めるのも同じ理由でダメ（狭めた分だけ中が見えなくなる）。

段の境目は「その距離から何m下まで見えるか」から決めてある。
目線 h・距離 d から幅 w の開口を覗くと見える深さは w·h/d。
w=1.47 / h=1.6 で 10m先=0.24m、6m先=0.39m、3m先=0.78m、1.5m先=1.57m。
0.40 / 1.60 で切ると 遠→近 で 水色 → 水色+青 → +濃紫 と段が増える。

**段どうしの差は温度差ではなくランプ上の距離で決まる。**
h = (T/70)^0.65 なので 12/7/3℃ は h=0.32/0.22/0.13 と下2段が近すぎ、
真上から見ると1色に潰れていた。底を 1℃(h=0.06) まで下げて濃紫に振ってある。

**⚠️ サーモの縦坑は「サーモから見て穴のマス」にだけ置く（`o == pass`）。**
他の役だけの穴にも置いていたせいで、**床があるはずの所に立ち上がりが
床から突き出て見えていた**。立ち上がりは踏み板より上に出るので、
「縦坑は全レイヤーに置いても踏み板に隠れる」という前提が成立しない。

**⚠️ 遠くから穴が見えるかどうかは、床より上に何かあるかで決まる。**

床より下の面は、距離が延びるほど**穴自身の手前の縁**に隠れる。
隠れ始める距離 = 開口幅 × 目線の高さ ÷ 深さ。
w=1.53m / h=1.6m なら y=0.06→41m、y=0.30→8m、y=1.10→**2.2m**。
斜面にしても同じで、**斜面の勾配が視線の勾配（目線÷距離）より急だと、
手前側の斜面が奥を隠す**。0.45m幅/0.18m落差（勾配0.41）にしたとき、
6m 先の穴は手前の斜面と視線がほぼ平行になって中が全く見えなくなった。

→ 縁を **床から 7cm 出っ張らせた**。床より上の物はどんな浅い角度でも
何にも隠されないので、部屋の反対側からでも輪郭線として読める。
サーモ層だけの見た目で、当たり判定には出ない（歩行の邪魔にならない）。

実測（room4・同条件で四方から見た点灯率）:

| | 出っ張り無し | 出っ張り有り |
|---|---|---|
| 入口(北)から | 12.1% | **15.3%** |
| 出口(南)から | 3.0% | **5.8%** |
| 西から | 6.4% | **8.8%** |
| 東から | 8.2% | **11.6%** |
| 穴の手前 | 22.5% | **28.8%** |

**⚠️ 縦坑の内壁は必ず両面を張ること**（`MeshBuild.Walls(..., bothSides:true)`）。
片面だと**見る向きによって内壁が消える**。実際、部屋の南側から見ると
穴の中がほとんど真っ黒になっていた。北側からは見えていたので気付きにくい。

### 9.6x サーモの踏み板は真っ黒にしない（08-29）

**⚠️ 落とし穴フロアの踏み板 `PitDeck` だけは、周囲の床と同じ dim=0.022
（＝ほぼ真っ黒）にしてはいけない。** 縦坑が dim=1.0 でくっきり見えるように
なった結果、**足場が真っ黒で穴だけが宙に浮いて見える**状態になっていた。
「パネルが浮いている」という指摘の一因はこれで、穴の側をいくら直しても消えない。
立っている面が見えないと穴との位置関係が読めず、深さの段も奥行きにならない。

現在: **34℃ / dim 0.130**（暗い緑）。
dim は明るさと同時に見える距離も決める（`range = lerp(5,200,dim²)`、
`range*0.45` から溶け始める）。0.13 なら **約3.7m から溶けて 8.3m で消える**。
＝足元と一歩先だけが見えて部屋の形は読めないので、
「空間の形はエコロケ役の担当」という切り分けは保たれる。

`PitDeck` を使うのは `BlindGimmickBuilder` の落とし穴フロアだけ。
他の部屋の床は `FloorStone`（dim 0.022）のままなので、影響はこの3室に閉じる。

### 9.6z エコロケがベタ塗りになる正体は「動的バッチング」（08-29）

**⚠️ 箱投影(`_UseObjectUv`)のマテリアルを2つ以上のオブジェクトで共有しないこと。**

Unity の動的バッチングは「同じマテリアル」で「300頂点未満」のメッシュを1つの
ドローコールに統合し、そのとき **頂点をワールド座標に焼き込んで
`unity_ObjectToWorld` を単位行列にする**。箱投影は `v.vertex` が
オブジェクト座標である前提なので、統合された瞬間に UV が 0〜1 から外れ、
面が丸ごと輪郭と判定されて最大輝度で塗り潰される。

実測（room5 の道路 Plane、エコロケ視点の「べた塗り」画素の割合）:

| | べた塗り |
|---|---|
| 道路1枚だけ | 0.3% |
| 同じマテリアルの板をもう1枚出す | **46.8%** |
| 同じマテリアルの板を全部出す | **69.4%** |

シェーダー側では直せない（統合後はオブジェクト座標が存在しない）。
`EchoMatFor` で **同じ部屋・同じメッシュの2個目以降は連番の別マテリアル**
（`Echo_room5_Plane_b1` …）にして、参照を分けてバッチングを断ち切ってある。

ついでに直した2点:

* **平たい物にシルエット発光(`_RimWeight`)を掛けない。** 床・地面・ポスターは
  必ず視線と浅い角度で見るので `dot(n,v)≈0` → rim≈1 になり面が飛ぶ。
  `_RimPower` を上げても `pow(≈1, n) ≈ 1` なので効かない。
  一番薄い辺が一番長い辺の 8% 以下なら重みを 0 にする。
**⚠️ 床をタイルに割っていいのは、床に穴が開いている部屋だけ。**
「床が読めないなら全部の部屋を格子に割ればいい」と一度やったが、
**どの部屋も同じ格子模様になって部屋どうしの区別が付かなくなった**
（room2 の廊下が落とし穴部屋とそっくりになった）。
エコロケ役の仕事は「今どこにいるか」を伝えることなので、
床の見た目が部屋ごとに違うことのほうが密度より大事。元に戻してある。

### 9.6ab ギミックを作り直したらエコロケ受信機を集め直す（08-29）

**⚠️ `BlindGimmickBuilder.BuildAll()` の最後で必ず

### 9.6y 穴の左右の偏りを均す（08-29）

「入口から見て左に偏っている」という指摘。実測で room4 は西→東が
**2/3/2/5/4/6 ＝ 22個中15個が東半分**。入口(北)から南を向くと東は左手なので、
そのまま「左に偏っている」と見えていた。手順4は「穴がゼロの列を作らない」
だけなので、この偏りは素通りしていた。

`Assign()` に3段構えで追加（いずれも**安全な道と locked は触らない**）:

| 手順 | 内容 | 動線への影響 |
|---|---|---|
| 5.7 | 多い列から1つ抜いて少ない列へ足す。差が1以下になるまで | 穴の総数・役の内訳は不変。safe は穴にしないので道は不変 |
| 5.8 | 役ごとに、多い列と少ない列で**担当を入れ替える** | どのマスが穴かは1マスも変わらない |
| 5.9 | 役ごとの**重心**を中央へ寄せる | 同上（入れ替えのみ） |

⚠️ 5.7 で「最多列と最少列の1組だけ見て、動かせなければ諦める」と書くと
まったく均されない（room9 は最多列の穴が全部 locked で1マスも動かなかった）。
**差が2以上ある組を総当たり**すること。差2以上でしか動かさないので振動はしない。

⚠️ 5.8 の「最大差」だけでは重心の偏りは取れない。
room4 のサーモは 0/1/2/1/2/2 で最大差2に満たないまま西端が空だった。
人が「偏っている」と感じるのは最大差ではなく重心なので 5.9 が要る。

それでも `seed` の出目そのものが悪いと寄せきれない。3室とも
**穴の総数を減らさない**ことを条件に種を総当たりして選び直した
（room4 5001→6626 / room9 10007→12660 / room14 18013→18580）。

結果:

|---|---|---|---|---|---|---|
| room4 (中央2.50) | 2.68 | 2.71 | **2.50** | 2.78 | 22 | 11歩/全歩が穴に隣接 |
| room9 (中央2.50) | **2.49** | 2.47 | **2.50** | **2.50** | 51 | 15歩/全歩が穴に隣接 |
| room14 (中央2.00) | **2.00** | **2.00** | **2.00** | **2.00** | 32 | 13歩/全歩が穴に隣接 |

### 9.6v 落とし穴フィールドは部屋の床いっぱいに取る（08-29）

**扉が列の中央に来るように nx を選ぶこと。**

### 9.6 簡易形状（箱）の落とし穴
バウンディングボックスで代用するので、
- **斜めに走る細い物**（レーザー・パイプ）は実体の何十倍もの板になる → `IsThinAndLong()` で除外
- **巨大な物**（8mのアヒル）は部屋を塞ぐ → `IsBig()` で除外
- **人体**を箱にすると「人の形」という情報が消える → `Body/Skin/Burning` は300三角形に粗くしてでも実形状

### 9.6ac U# をスクリプトから足すときは同期方式を明示する（09-07）

**⚠️ `[UdonBehaviourSyncMode(BehaviourSyncMode.Manual)]` を書いても、
スクリプトから `AddComponent` した UdonBehaviour には反映されない。**

U# のプログラム資産(`*.asset`)は Manual になっているのに、実体は
**Continuous のまま**だった。Continuous だと `OnDeserialization` が毎フレーム飛ぶので、
「同期が来た瞬間だけ処理する」書き方が全部壊れる
（だるまはオーナー以外の画面で振り向き途中のまま固まる）。

`BlindGimmickBuilder.SetSyncMode(beh, "Manual")` で実体の `_syncMethod` を直接書くこと。
enum名は `Unknown / None / Continuous / Manual`。
同期変数が1つも無い物（コヨーテタイム）は `"None"` にする。

**⚠️ 新しい U# スクリプトを足したら `*.asset`（プログラム資産）も要る。**
無いまま `AddUdon` すると
`Unable to find valid U# program asset associated with script` で NullReference になる。
`UdonSharp.UdonSharpProgramAsset` を `CreateInstance` して `sourceCsScript` に
`MonoScript` を入れ、`AssetDatabase.CreateAsset` → `CompileAllCsPrograms(true,false)`。

### 9.8 コヨーテタイム（09-07）

`Assets/_BLIND/Scripts/CoyoteTimeAssist.cs`。`=== SYSTEM ===/GameManagement/Gimmicks/CoyoteTime` に1個。
足場を離れてから **0.20秒** はジャンプ入力を受け付け、本来と同じ初速を与える。

落とし穴部屋は「他の2人の声を聞いてから跳ぶ」設計なので、
**入力が一瞬遅れるのが正しい遊び方**になっている。素の VRChat は接地していない
瞬間の入力を捨てるので、その遅れがそのまま落下＝全員リスポーンになっていた。

**⚠️ 接地中の入力には絶対に触らないこと。**
接地中は VRChat 本体がジャンプさせるので、こちらでも初速を足すと二段ジャンプになり、
穴を跳び越え放題になって落とし穴部屋が成立しなくなる。
`InputJump` の中で `IsPlayerGrounded()` が true なら**何も覚えずに捨てる**。
判定は本体と同じ API を使って食い違いを避ける。
1回空中に出るごとに1回だけ（`usedThisAirtime`）。これが無いと連打で浮き続けられる。

### 9.9 だるまさんがころんだ（room11・09-07）

`Assets/_BLIND/Scripts/DarumaWatcher.cs` ＋ `BlindGimmickBuilder.BuildDarumaWatcher`。
生成物は `room11/DarumaWatcher_Generated`（`ギミック/1` で作り直される）。

背を向ける(4.5〜9秒) → 振り向く(0.9秒) → 見張る(2.5〜5秒) を繰り返し、
見張り中に **水平方向に 0.30m** 動いた人を名指しする。
振り向き切ってから 1.0秒 は猶予（止まる余裕）。1周 7.9〜14.9秒。

**⚠️ この部屋では死なない（`punish` 既定 false）。意図した設計であって、消し忘れではない。**

- この部屋はゲートボタン(＝復帰地点)を押す**前**にある。ここで死ぬと、
  **まだ稼いでいない進行度まで巻き戻る**形になり、失うものが大きすぎる。
- そもそも復帰地点 `CP_2_Blue` がこの部屋の中にあるので、死んでも部屋の中に
  戻るだけで罰として成立していない。
- 「一歩ごとに死ぬ」緊張は落とし穴部屋(room4/9/14)の担当。
  ここまで即死だとテンポが単調になる。

捕まったときの手応えは**「だるまが自分の方を向いて指す」**ことで足りている。
3人は互いが見えないので、**誰が動いたかが分かること自体**が情報になる。
罰を付けたくなったら `punish` を入れるだけ（`checkpointManager` の結線は残してある）。

#### ⚠️ 「扉を入った瞬間に死ぬ」を二度とやらないために

最初の版は**入室した瞬間に死ぬ**うえ、**復帰してもまた即死する無限ループ**になり、
確認も調整も一切できない状態だった。原因は2つ重なっていた。

1. **判定を「今 部屋の中か」で毎フレーム見ていた。**
   見張り中（1周の約3割）に部屋へ入ると、歩いている最中の位置がそのまま基準として
   固定され、次の瞬間には 0.3m 動いていて即アウトになる。
   → **判定の対象は「見張りが始まった瞬間」に決める**（`eligible`）。
   その時点で既に部屋にいて、かつ入室から `enterGrace` 2.5秒たった人だけ。
   途中から入った人は次の回から参加する。

2. **復帰地点 `CP_2_Blue` がこの部屋の判定ゾーンの中にあった**
   （ゾーンは `x[6.3,14.1] z[-57.7,-37.9]`）。青のゲートボタンが room11 に
   自動配置されていたため。死んでも部屋の外に出ないので**ゾーンを出入りせず、
   `OnPlayerTriggerEnter` が飛ばない**＝入室の猶予が働かなかった。
   → 名指しの瞬間に全クライアントで `insideSince` を取り直し、復帰した人にも
   もう一度猶予を与える。加えて捕まった直後の「背を向ける」は必ず `awayMax`(9秒) にする。
   → **さらに、青ボタン自体を room12 へ出した（下記 9.11）。**

（現在は `punish` を切ってあるので即死は起きないが、
入れ直したときに同じ穴に落ちないよう、上の2つの対策は残してある。）

### 9.11 ⚠️ ゲートボタンの自動配置は「空いている床」しか見ていない（09-07）

`BuildGateButtons` は `FindOpenSpot` で**部屋の中で一番広く空いている床**を選ぶだけで、
**そこが部屋として妥当な位置かは一切見ていない**。

実害:
- 青ボタンが room11(だるま部屋)の**ど真ん中(9.7, -47.0)＝だるまの正面**に置かれていた。
- 作者の設計にだるま部屋のボタンは存在しない。**ビルダーが勝手に生やした物**。
- そのせいで部屋が「ボタン前」と「ボタン後」に分断され、一続きの緊張が切れていた。
- 復帰地点も道連れで部屋の中に入り、上の即死ループの一因になった。

対策として `ButtonSpec.at` を足した。`Vector3.zero` 以外なら自動配置をやめてそこに置く。
青は `room12` の入口すぐ `(15.0, 0, -43.6)` に移してある
（実測で周囲3.24m空き。room11 の最良地点でも1.14mしかなかった）。

**⚠️ ボタンを消してはいけない。** 赤・青・緑の3つ全部が押されると room3 の
シャッターが開く（`ColorGateButton` → `MultiButtonDoor`）。
1つでも欠けるとクリア不能になる。要らない場所にあるなら**消すのではなく `at` で動かす**。

**⚠️ `ギミック/1` は毎回この GameObject を作り直すので、
インスペクタで直した値は次のビルドで既定値に戻る。**
恒久的に変えたいときは `DarumaWatcher.cs` / `DarumaCrowd.cs` の既定値を書き換えること。

**このギミックの肝は「だるまが、動いた人の方を向く」こと。**
3人は互いの姿が見えないので、**誰がやったかを知る手段が向きしかない**。
名指し中(1.4秒)は `VRCPlayerApi.GetPlayerById(accusedId)` の位置を毎フレーム追う。

**⚠️ だるまはシルエットが前後でほぼ同じ。**
過去人はテクスチャの顔で向きが分かるが、サーモ役は単色の塊、
エコロケ役は輪郭しか見えないので**どちらを向いているか判別できない**。
向きが全てのギミックなので致命的だった。対策は層ごとに別:

- **サーモ**: 元の絵から温度差を作る（下の 9.10）。赤い胴=橙〜赤 / 白い顔=黄緑 /
  黒目・黒眉=青 になり、サーモ画面でもちゃんと「だるまの顔」として読める。
  **板を貼ってはいけない**（せっかくの顔を塗り潰す）。
- **エコロケ**: 顔の位置に板(`Boss/E_Face`)。輪郭しか出ない層では絵が使えないので、
  向いている間だけ四角い輪郭が出るようにする。背を向けると胴体に隠れる。
- **過去人**: 何もしない。元の絵がそのまま見える。

**⚠️ サーモの本体は `Prop`(19℃ dim 0.095) にしてはいけない。**
dim が小さい物は数mで背景に溶けるので、20mの廊下の奥のだるまが見えず、
「今こっちを向いた」を3人で共有できない。専用の `Watcher`(33℃ dim 0.9) を使う。

その他の判断:
- **判定ゾーンは部屋いっぱいのトリガー。** これが無いと別の部屋を歩いているだけの人が
  「動いた」と判定される。`OnPlayerTriggerEnter` はトリガーが付いている GameObject の
  UdonBehaviour にしか飛ばないので、コライダーと `DarumaWatcher` は同じ GameObject に置く。
- **位相はオーナーだけが進めて同期する。** 全員が自前でタイマーを回すと数秒でズレて
  「自分だけ捕まる」ようになる。回転は同期せず各自が位相から計算する。
- **設置位置は扉から 2.4m 以上離す。** 空きだけで選ぶと一番物が無い＝扉の前が選ばれ、
  実際に出口(14.2, -39.8)の真ん前に立って通路を塞いでいた。
- 音は未実装。`chantSound` / `caughtSound` を挿せば鳴る。

#### ⚠️ 「振り向いた瞬間」が見えないとただの理不尽な即死になる

実測（12m・サーモ）で、振り向きの途中経過を撮って顔として読める画素を数えた:

| 振り向き | 0% | 25% | 50% | 75% | 100% |
|---|---|---|---|---|---|
| 顔の画素 | 135 | 167 | 182 | 650 | 918 |

**増えるのは後半40%だけ**で、前半はほとんど変化が無い。
さらに**エコロケ役はパルスが当たっていないと何も見えない**ので、
たまたま撃っていなければ振り向きを丸ごと見逃して死ぬ。

対策（`DarumaWatcher`）:

- **サーモ**: 振り向いている間だけ `_HeatIntensity` を上げる（`turnHeat` 1.45）。
  MaterialPropertyBlock なので他のだるまには影響しない。
  実測で中央の明るさ 0.289 → 0.380、白飛び 0px → 1228px。
  0.45秒だけ真っ白に飛んでから、`watchHeat` 1.15 で顔が読める状態に落ち着く。
  **暗い → 白く発光 → 顔が見える** という順になり、見逃しようが無い。
- **エコロケ**: 振り向いた瞬間に受信機を強制点灯（`TriggerGlowWithDelay(0, 0.35)`）。
  パルス待ちにしない。「だるまが動けば音が出る＝反響が返る」という理屈にも合う。
- 立ち上がりは即・戻りはゆっくりにしてある（`shownHeat`）。点いた瞬間が目に留まる。

### 9.10 だるまの群れ（97体）と「絵から温度を作る」（09-07）

`Assets/_BLIND/Scripts/DarumaCrowd.cs` ＋ `BlindGimmickBuilder.BuildDarumaCrowd`。
棚や机の上の**だるま97体が、その場から動かずに首だけこちらを向く**。

**⚠️ サーモ・エコロケの複製は「本体の子」として作ること。**
`vision/2` に任せると部屋直下の `Vision_Thermal` に1枚のメッシュとして結合されるので、
本体が首を回しても**複製は取り残され、過去人だけが「こっち向いた」と言う嘘になる**。
そのため `Prop_Daruma` は `IsGimmickOwned` で vision から除外し、
本体の子に `DarumaVision_Generated`（T_Body / E_Body）を作っている。
結合できないぶん描画数は増えるが、だるまは元から軽く（平均426三角形）
2層合わせて 82,636 三角形で収まる。

**⚠️ 向きは同期しない。各クライアントが自分のプレイヤーの方を向かせる。**
3人はそれぞれ別の世界を見ているので合わせる必要が無い。
97体ぶんの回転を同期すると帯域を使い切るし、遅延でガクガクになる。
`BehaviourSyncMode.None`。

**⚠️ なめらかに回してはいけない。カクッと動かすこと。**
最初は 80度/秒 で連続的に回していたが、それだと
**「気付いたら向きが変わっていた」になり、動いた瞬間がどの役にも見えない**。
サーモは1フレームあたりの面の変化が小さすぎ、エコロケはそもそもパルスが
当たっていないと何も見えない。止まっている物が一瞬でカクッと動くほうが必ず目に留まる。

現在: 1回 `snapAngle` 32度ずつ、次までの間隔は体ごとに 0.9〜2.2秒でばらつかせる。
`deadZone` 8度以内になったら動かない（**これが無いと永久にカクカクし続ける**）。
動いた瞬間にその体のエコロケ受信機を点灯（`TriggerGlowWithDelay(0, 0.15)`）。
向き終われば光らなくなるので、部屋が光りっぱなしにはならない。
＝**入室直後はあちこちで光り、落ち着き、こちらが動くとまた光る。**

その他:
- **`rotation` を代入し直さないこと。** 棚のだるまは少し傾けて置いてあり、
  `Quaternion.Euler(0,yaw,0)` を代入すると全部が直立に揃って「置いてある感」が消える。
  ワールドY軸まわりに**差分だけ**回す（`Quaternion.AngleAxis(delta, up) * rotation`）。
- 1フレーム12体ずつ見る。97体を毎フレーム見ると重い。
- 14m まで近づくまで回らない。部屋の外から全部こちらを向いていると驚きが無い。

#### 絵から温度差を作る（`ThermalSurface` の `_AlbedoTex` / `_TempByRed` / `_TempByDark`）

一様な温度で塗ると模様のある物が「のっぺりした塊」になる。
だるまは**顔が読めること自体がギミック**なので、絵から温度差を作る。
既定は 0 なので、指定しないマテリアルの見え方は一切変わらない。

**⚠️ 引っかかった点が2つある。**

1. **Linear 色空間では `tex2D` がリニア値を返す。**
   そのまま使うと「絵の上では鮮やかな朱色」が r=0.32 にしかならず赤さが出ない。
   `LinearToGammaSpace()` で sRGB に戻してから判定する。
2. **暗さの減算は彩度の低い所にだけ効かせる。**
   素の `(1 - 輝度)` で引くと、**濃い赤は輝度が 0.25 しかないので
   「暗い」と判定されて赤さの加算を打ち消し、胴が緑になる**（実際そうなった）。
   `(1 - 輝度) × (1 - 彩度)` にして、黒目・黒眉だけを冷やす。

現在の値: `_TempByRed 33` / `_TempByDark 16` / 赤さは `×1.8` して 0.55 で頭打ち。
胴がランプの 0.91＝赤（白飛びは 0.93 から）に乗る。
だるまは種類ごとにテクスチャが違うので、`ThermalDarumaMat()` が絵ごとに材質を分ける。

温度は監視者 `Watcher` 33℃ / 群れ `Daruma` 26℃。
**群れを一段暗くしてあるのは、どれが本体か分かるようにするため。**

### 9.12 持ち帰る鍵（room11・09-07）

`BlindKeyBaker`（`BLIND/鍵/1. 真鍮の鍵を焼く`）で手続き生成。
外部素材を使わないのはライセンス表記の管理を増やさないため。
320三角形 / 10.9×14.7cm / サブメッシュ 0=真鍮 1=札。
設置は `BlindGimmickBuilder.BuildKeyProp`（`room11/KeyProp_Generated`）。

**⚠️ 小さい物は「明るくする」だけでは見つからない。白飛びさせること。**
30℃(緑 dim0.95) で試したが、11cm の鍵は 4.5m 先で 15px にしかならず、
暗い画面の緑の点は**見分けが付かなかった**（実測）。
白飛びが始まる 64.1℃ を超える **66℃** にして「黒い部屋の白い点」にしてある。

**⚠️ さらに、まわりのだるまを撤去しないと埋もれる。**
棚はだるまで埋まっていて、白飛びさせても周囲の暖色に紛れて見えなかった。
`BuildKeyProp` が半径0.95m のだるまをどけて、
**その棚だけ何も無い**状態を作る。空きそのものが目印になる。

**⚠️ 鍵の設置は群れの配線より先に呼ぶこと。**
鍵がだるまを消すので、順序が逆だと `DarumaCrowd.darumas` に
消えたはずのだるまが残って null になる。

#### 運搬（`CarryableItem`）

鍵・アヒルなど「拾って別の場所へ持っていく」物の共通スクリプト。
掴む／投げる／受け渡すは VRChat 標準の `VRCPickup` が全部やるので、
こちらは**無くさないための後始末**（床下へ抜けた・遠くへ投げ捨てられたら置き場所へ戻す）だけ。

**⚠️ `VRCPickup` だけでは位置が同期しない。必ず `VRCObjectSync` も付けること。**
付け忘れると「自分だけ鍵を持っていて、他の2人には棚に置いたまま見える」という、
この作品でいちばん厄介な種類の食い違いになる。
`CarryableItem` 自体は同期しない(None)。位置は ObjectSync の担当で、二重にすると取り合う。

**⚠️ 書架の当たり判定は「棚1台まるごと1個の箱」（高さ2.1m）。棚板の間に手は入らない。**
棚の内側に物を置くと**見えているのに絶対に取れない**。
コライダーの外、棚板の手前のふちに置くこと（`BuildKeyProp` が自動で外へ出す）。
そこは棚に支えられないので、ごく薄い受け皿(`Ledge`)を一緒に置いて落下を防いでいる。

### 9.7 検証は目視で済ませない
これまでのバグは全て「エディタ上は正常に見えた」もの。
一時カメラでレイヤー別スクリーンショットを撮り、中心ピクセルを数値で比較する。
オブジェクトを1つずつ無効化して輝度の変化を見る二分探索が有効（`t_room14` の白飛び特定はこれで解決した）。

**注意**：エコロケの検証で全受信機の `_GlowIntensity` を1にすると**マップ全体が光る**ので、遠くの部屋まで写って誤診する。実機では12m以内しか光らない。

## 13. チームメンバーからの引き継ぎ指示（2026-08-21付、実装状況を追記）

以下は08-21深夜時点でチームメンバーが残した指示。**大部分は実装済み**（§7.5参照）。指示原文はそのまま残し、実装状況を各項目に追記した。

### 落とし穴と普通の穴への付与
- **普通の穴**: 床に当たり判定をなくして、エコロケは与えない。
- **落とし穴**: 床に当たり判定をなくして、エコロケを与えて、サーモを渡す。

→ **実装済み**（`PitField_Generated`、room5/10/18）。ただし実装したロジックは上記の「普通の穴／落とし穴」の区別ではなく、**役職ごとに異なるマスを穴にする**（過去人だけの穴・サーモだけの穴・エコロケだけの穴を1つの穴フィールド内に混在させる）方式になっている。指示の意図と食い違っている可能性があるので、本人に「これで良いか」を確認すること。食い違っていれば `BlindGimmickBuilder.cs` の `Assign()` を書き換える。

### クイズとドア
ドアを全部閉めた状態にしてから、ゲームマネージャーとドアとリスポン地点に付与する。問題文と選択肢の貼り付け。
- **DoorQuizChoice**（ドア1枚ごとに付ける）
  - プレイヤーがInteractしたら、自分の番号を `DoorQuizManager` に送る。
  - `doorQuizManager` — このドアが属する `DoorQuizManager` をドラッグ
  - `doorIndex` — このドアの番号（0, 1, 2）
- **DoorQuizManager**（1問につき1つ配置）
  - 選択されたドア番号と正解を比較し、正解→ドアを移動、不正解→全員チェックポイントへ戻す。
  - `correctDoorIndex` — 正解のドア番号（0, 1, 2）
  - `door0` / `door1` / `door2` — 3枚のドアのTransformをドラッグ
  - `door0OpenPosition` / `door1OpenPosition` / `door2OpenPosition` — ドアの開いた位置のVector3（正解ドアのみ実際に使用される）
  - `checkpointManager` — シーン内の `CheckpointManager` をドラッグ
  - `correctSound` / `wrongSound` — 正解時・不正解時の音（任意）

→ **`QuizManager1/2/3` として3問配置済み**（room13ほか）。ただし **`checkpointManager` が空の方の `CheckpointManager` を指していて機能していない**（§7.5の致命的バグ）。`correctDoorIndex` が3問とも0固定、不正解側の open position がプレースホルダのまま、`correctSound`/`wrongSound` 未設定、問題文UIが見当たらない、という点も未解決。**`DoorQuizChoice` が各ドアに付いているかは未確認**（本節作成時はシーン内で `DoorQuizChoice` のスクリプト参照を見つけられなかった）。

### 各種ドアとボタン（対応するドアとボタンにコンポーネント付与）
- **MultiButtonDoor**
  - GameObjectにアタッチする。複数のボタンがインタラクトされてand回路でドアを開閉する。
  - 移動させるドアとドアの開閉時の座標を設定できる。開閉時の効果音も設定できる。
- **MultiButtonDoorButton**
  - ボタンにアタッチする。ボタンIDで重複を避ける。ボタン押した時の効果音を設定できる。
- **SingleButtonDoor** / **SingleButtonDoorButton** / **SingleButtonDualDoor** / **SingleButtonDualDoorButton**

→ **`MultiButtonDoor` はroom3のシャッターに実装済み**。ただし専用の `MultiButtonDoorButton` ではなく、赤/青/緑の見た目とチェックポイント登録を兼ねる `ColorGateButton`（新規スクリプト）をボタン側に使っている。`SingleButtonDoor` 系は**シーン内に一つも使用箇所が無い**（§7.5）。

### CheckpointManager（シーンに1つ）
不正解時などに `TriggerDeath()` が呼ばれ、全員を現在のセーブポイントにテレポートさせる。
- `checkpoints` — Transform配列。[0] はスタート地点（復帰先、空のGameObject）。[1] 以降は各セーブポイント。
- `doors` — 進行で開閉するToggleDoor（なければ空）
